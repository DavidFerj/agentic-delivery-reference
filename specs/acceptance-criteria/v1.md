# Version 1 Acceptance Criteria

## Product flow

- **AC-001:** Given an authenticated requester, when a valid request is submitted, then a workflow is created and its identifier and initial status are returned.
- **AC-002:** Given invalid or oversized input, when it is submitted, then no workflow executes and a safe validation response is returned.
- **AC-003:** Given a valid workflow in local mode, when it runs, then it uses the deterministic provider and produces a schema-valid proposal.
- **AC-004:** Given relevant knowledge, when the proposal is produced, then the response contains verifiable citations to retrieved sources.
- **AC-005:** Given a proposed ticket action, when no authorized approval exists, then the action is not executed and the workflow remains paused.
- **AC-006:** Given an authorized approval, when it is consumed, then the workflow resumes once and the simulated ticket is created once.
- **AC-007:** Given a rejection or expired approval, when processing continues, then no ticket is created and the decision is visible and audited.
- **AC-008:** Given a retried worker delivery, when the same idempotency key is processed, then no duplicate side effect is created.

## Access and security

- **AC-009:** Given an anonymous or invalidly authenticated caller, when a protected endpoint is called, then access is denied.
- **AC-010:** Given an authenticated user without permission, when a protected resource or approval is requested, then access is denied and audited without exposing the resource.
- **AC-011:** Given a prompt-injection attempt in a request or retrieved document, when the workflow runs, then unauthorized tool execution is blocked by deterministic policy.
- **AC-012:** Given logs and traces from representative executions, then configured secrets and sensitive fields are absent.

## Evidence and quality

- **AC-013:** Given a completed workflow, then the console shows the request, result, citations, state history, approvals, latency, token estimate, cost estimate, and correlation ID permitted to the user.
- **AC-014:** Given the golden set, when evaluation runs, then normal, boundary, failure, and adversarial cases produce a versioned report.
- **AC-015:** Given a result below a required quality or safety threshold, when CI runs, then CI fails.
- **AC-016:** Given an implemented capability, then `capability-map.yaml` links its source, tests, demo, documentation, and evidence.

## Delivery

- **AC-017:** Given a clean supported development machine, when documented local setup steps are followed, then the system starts without a paid external service.
- **AC-018:** Given the development GCP prerequisites, when the documented infrastructure plan is applied with authorized credentials, then independently deployable web, API, worker, and evaluator resources are created.
- **AC-019:** Given a failed cloud revision, when the rollback runbook is followed, then traffic can return to the previously verified revision without data rollback.
- **AC-020:** Given disabled n8n, Vapi, MCP, ticketing, or real-model configuration, then the system uses its supported simulator or reports the feature as unavailable without unsafe fallback.

## Phase 0 acceptance

- **AC0-001:** Product objective, users, journey, MVP, exclusions, and success measures are documented.
- **AC0-002:** Functional and non-functional requirements have stable identifiers.
- **AC0-003:** The workflow state model defines valid transitions and invariants.
- **AC0-004:** A versioned OpenAPI contract describes the initial HTTP boundary.
- **AC0-005:** The test plan maps acceptance criteria to planned validation levels.
- **AC0-006:** The threat model identifies assets, actors, entry points, trust boundaries, abuse cases, mitigations, and residual risks.
- **AC0-007:** Architectural decisions explain deployable boundaries, integration isolation, persistence choices, and AI framework choices.
- **AC0-008:** The capability registry represents planned capabilities without claiming unimplemented evidence.
